# 06 · 路由守卫状态缓存

- 优先级：P2
- 类型：性能
- 依赖：无
- 影响文件：`middleware/unlocked.ts`、`composables/usePassphrase.ts`

## 问题

`middleware/unlocked.ts:9-12` 在每次客户端导航时都请求一次 `/api/status`。页面间来回切换会重复产生请求，虽然单次很便宜，但完全没必要。

## 方案

复用 `usePassphrase()` 的模块级单例状态（`unlocked` / `ready` / `inflight`）。

### 1. `usePassphrase.refresh` 支持缓存

```ts
async function refresh(force = false) {
  if (!force && ready.value) return
  if (inflight) return inflight
  // ...原逻辑
}
```

同时新增 `markUnlocked(value: boolean)`（或直接暴露 ref 让守卫写入），在 `tryUnlock` / `lock` 成功后更新 `ready`。

### 2. 守卫逻辑

```ts
export default defineNuxtRouteMiddleware(async (to) => {
  if (to.path === '/') return

  const { unlocked, ready } = usePassphrase()

  // 客户端已有可信状态：不再请求
  if (import.meta.client && ready.value) {
    if (!unlocked.value) return navigateTo('/')
    return
  }

  const request = import.meta.server ? useRequestFetch() : $fetch
  try {
    const res = await request<{ unlocked: boolean }>('/api/status')
    if (import.meta.client) {
      unlocked.value = !!res?.unlocked
      ready.value = true
    }
    if (!res?.unlocked) return navigateTo('/')
  } catch {
    if (import.meta.client) {
      unlocked.value = false
      ready.value = true
    }
    return navigateTo('/')
  }
})
```

### 3. 状态失效

- `lock()` 已把 `unlocked` 置 false，`ready` 保持 true，守卫会直接重定向。
- `tryUnlock()` 成功后 `unlocked = true`，后续导航不再请求。
- Cookie 在 180 天后过期，但页面可能一直开着；可接受。若需要更严格，可在 `visibilitychange` 时强制 `refresh(true)`，本批次不做。
- 服务端（SSR）仍按请求单独校验，因为模块状态不跨请求共享。

## 验收标准

- [ ] 首次从 `/` 进入 `/memo` 时请求一次 `/api/status`。
- [ ] 在 `/memo` ⇄ `/goals` ⇄ `/likes` 之间切换时不再产生 `/api/status` 请求。
- [ ] 直接刷新 `/memo`（SSR）时仍能正确放行或重定向。
- [ ] 点击「锁定」后立即跳回封面，再次访问内页不会误解锁。
- [ ] 硬刷新后状态正确重建。

## 风险与回滚

- 缓存的是「本进程内」状态；多标签页之间不同步（一个标签锁定，另一个仍认为已解锁）。Cookie 本身已被服务端删除，下一次服务端校验或刷新会纠正。
- 回滚：守卫恢复为每次请求 `/api/status`。
